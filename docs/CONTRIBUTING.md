# Contributing Guide

> 초안입니다. 각 항목은 팀원이 나눠 PR로 보완합니다.

## 브랜치 전략 (GitHub Flow)

- `main`: 검증된 작업만 모으는 브랜치. 직접 push 금지, PR로만 병합(승인 1명 이상).
- `feature/이름-작업내용`: 작업 단위 브랜치. 최신 main에서 만들고, 병합 후 삭제.
- GitHub Flow를 선택한 이유 (3줄 이내):
  - (작성 예정)

## 작업 단위

- 목적이 하나이고 독립적으로 검토·검증할 수 있는 변경 하나 = Issue 1개 = 브랜치 1개 = PR 1개.

## 브랜치 네이밍

- 형식: `feature/이름-작업내용` (영문 소문자, 단어는 `-`로 연결)
- 예: `feature/seoyeon-average`, `feature/jeongmin-study-time`

## 커밋 메시지 컨벤션

- 형식: `<type>: <무엇을 바꿨는지 구체적으로>`
- type: `feat`(기능), `fix`(수정), `docs`(문서), `refactor`(구조 개선), `chore`(설정·기타)
- 예: `feat: 점수 평균 계산 함수 추가`
- 금지: `update`, `fix`, `wip`, `완료`처럼 대상이 불분명한 메시지만 쓰기

## PR 규칙

- 본문에 What·Why·How와 `Closes #실제번호` 포함 (PR 템플릿 사용)
- 다른 팀원 1명 이상 승인 + 리뷰 의견 처리 후, PR 작성자가 병합
- 공유 브랜치의 기록 재작성, 합의 없는 강제 push·리베이스 금지

## 코드 리뷰 규칙

- 파일·라인·동작을 근거로 질문이나 개선 의견 최소 1개 (`LGTM`, `좋아요`만 쓰기 금지)
- 작성자는 리뷰에 답변하고, 수정했다면 변경 내용과 검증 결과를 남김

## 충돌 대응 흐름

관련 팀원에게 공유 → 변경 의도 확인·해결 → 검증 → `docs/conflict-resolution.md`에 기록
