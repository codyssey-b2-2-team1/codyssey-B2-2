# Contributing Guide

윤정민이 작성한 기본 규칙에 팀 역할·구현 기준·실습·제출 증빙 규칙을 보완한 문서입니다. 각 항목은 팀원이 나눠 검토하고 PR로 보완합니다.

## 팀 정보와 역할 분담

- 프로젝트: 학생용 학습 도우미 함수 모음 (Python 3.10 이상)
- 공동 저장소: https://github.com/codyssey-b2-2-team1/codyssey-B2-2
- 팀장: 윤정민. 팀장도 다른 팀원과 동일한 PR·리뷰·승인 규칙을 따릅니다.

| 역할 | 이름 | GitHub 아이디 | 담당 기능 | 후속 문서 정리 책임 |
| --- | --- | --- | --- | --- |
| A | 강서연 | `5312ksy-beep` | 점수 평균 계산 | 협업 가이드 보완 |
| B | 김수민 | `cody2620` | 마감일까지 남은 날짜 계산 | 충돌 해결 기록 |
| C | 윤정민 | `yj-min-i` | 공부 시간 변환 | 트러블슈팅 기록 |
| D | 임재홍 | `sarguments` | 과제 진행률 계산 | README·SUBMISSION.md |

- 기본 리뷰 배정: 김수민 → 강서연 PR, 윤정민 → 김수민 PR, 임재홍 → 윤정민 PR, 강서연 → 임재홍 PR.
- 지정 리뷰어가 참여하기 어려우면 작성자 외 다른 팀원에게 요청하고 PR에 남깁니다.
- 문서 담당은 정리 책임자입니다. 실습 참여자는 본인의 수행 내용과 증빙을 직접 제공하고 이름·역할을 기록합니다.
- 협업 가이드도 팀원이 분담하여 실제 제안·수정 기록을 남깁니다. 이 문서의 초안이나 취합만으로 다른 사람의 작성 참여를 대신하지 않습니다.

## 브랜치 전략 (GitHub Flow)

- `main`: 검증된 작업만 모으는 브랜치. 직접 push 금지, PR로만 병합(승인 1명 이상).
- `feature/이름-작업내용`: 작업 단위 브랜치. 최신 main에서 만들고, 병합 후 필요에 따라 삭제하거나 보관합니다.
- GitHub Flow를 선택한 이유 (3줄 이내):
  - 작업 브랜치를 나눠 각자 독립적으로 작업할 수 있습니다.
  - PR과 리뷰로 변경 의도와 검증 결과를 공유할 수 있습니다.
  - 검증된 변경만 합쳐 main을 항상 실행·사용 가능한 상태로 유지할 수 있습니다.

## 작업 단위

- 목적이 하나이고 독립적으로 검토·검증할 수 있는 변경 하나 = Issue 1개 = 브랜치 1개 = PR 1개.
- 예: 평균 함수와 해당 사용 예시는 같은 작업이며, 관련 없는 협업 문서 보완은 별도 작업입니다.
- 리뷰에 따른 수정은 같은 브랜치와 PR에서 이어갑니다. 수정 커밋마다 PR을 새로 만들지 않습니다.
- Issue에는 담당자, 작업 범위, 동작 기준, 완료 기준을 적습니다. 합의한 동작을 바꿀 때는 Issue에서 먼저 공유합니다.

## 브랜치 네이밍

- 형식: `feature/이름-작업내용` (영문 소문자, 단어는 `-`로 연결)
- 예: `feature/seoyeon-average`, `feature/jeongmin-study-time`

## 커밋 메시지 컨벤션

- 형식: `<type>: <무엇을 바꿨는지 구체적으로>`
- type: `feat`(기능), `fix`(수정), `docs`(문서), `refactor`(구조 개선), `chore`(설정·기타)
- 예: `feat: 점수 평균 계산 함수 추가`
- 금지: `update`, `fix`, `wip`, `완료`처럼 대상이 불분명한 메시지만 쓰기

## PR 규칙

- 본문에 What·Why·How와 `Closes #실제번호` 포함 (PR 템플릿 사용)
- 다른 팀원 1명 이상 승인 + 리뷰 의견 처리 후, PR 작성자가 병합
- 공유 브랜치의 기록 재작성, 합의 없는 강제 push·리베이스 금지
- 관리 권한이 있는 팀원도 main 보호 규칙을 우회하지 않습니다.
- PR에 실제로 확인한 입력·절차, 기대 결과와 실제 결과를 기록합니다. 문서 변경은 링크·경로·요구 항목·Markdown 표시를 확인합니다.
- 본문 양식은 `.github/pull_request_template.md`를 따르며, 자리표시자를 실제 내용과 Issue 번호로 바꿉니다.

## 코드 리뷰 규칙

- 파일·라인·동작을 근거로 질문이나 개선 의견 최소 1개 (`LGTM`, `좋아요`만 쓰기 금지)
- 작성자는 리뷰에 답변하고, 수정했다면 변경 내용과 검증 결과를 남김
- 모든 PR에서 리뷰어와 작성자 사이의 답변 또는 수정 반영이 최소 1회 기록되어야 합니다.
- 리뷰어는 최종 수정 내용을 확인하고 승인합니다. 승인 후 중요한 변경이 생기면 다시 확인을 요청합니다.
- 형식적인 지적을 만들기보다 입력 검증, 예외 처리, 사용 예시, 설명과 실제 동작의 일치를 확인합니다.

## 충돌 대응 흐름

관련 팀원에게 공유 → 변경 의도 확인·해결 → 검증 → `docs/conflict-resolution.md`에 기록

- 충돌을 발견한 사람이 대상 브랜치·파일·상황을 공유하고, 양쪽 작성자가 필요한 최종 동작을 함께 정합니다.
- 최신 수정이라는 이유만으로 한쪽을 선택하지 않습니다. 합의한 요구사항과 양쪽 변경 의도를 기준으로 통합·선택합니다.
- 해결 후 충돌 마커를 제거하고 관련 함수·문서를 검증합니다. 해결 커밋을 올리고 리뷰어가 확인합니다.
- 기록 항목: 참여자, 시작 커밋·브랜치·파일, 재현 절차, 충돌 내용, 수행 명령·해결 절차, 선택 이유, 검증 결과, PR·커밋 링크, 배운 점.
- 팀 전체 최소 2회 기록을 남기며, 최소 1회는 같은 파일의 같은 hunk(인접 구간) 수정 또는 이동·이름 변경·삭제와 내용 수정이 겹치는 비자명 충돌 조건을 충족합니다.
- 실습 계획: 강서연·김수민 1회, 윤정민·임재홍 1회. 대상 구간과 시점은 대면 때 함께 정합니다.
- 같은 구간의 충돌이 반복되면 담당 범위, PR 크기, 브랜치 유지 기간과 병합 순서를 조정합니다.

## 구현·검증 공통 기준

- 함수 입력이 잘못된 경우 예외는 `ValueError`로 통일합니다. 잘못된 자료형·값·날짜 형식도 포함하며, `"ValueError"` 문자열을 반환하는 방식으로 처리하지 않습니다.
- 숫자 입력에서 `True`와 `False`는 허용하지 않습니다. Python의 bool은 int의 하위 타입이므로 숫자 검사 전에 별도로 제외합니다.
- 진행률은 0~1 비율이 아닌 **퍼센트 단위의 숫자**로 반환합니다. 예: `calculate_progress(3, 4)` → `75.0`.
- 기능별 범위·반올림·빈 입력 처리 등은 해당 Issue의 동작 기준을 따릅니다.
- 각 함수에 사용 예시를 남기고 정상 입력과 경계·오류 입력을 확인합니다. 숫자 입력 함수는 bool 거부도 확인합니다.

## 트러블슈팅 실습과 기록

| 시나리오 | 기본 담당 | 확인할 내용 |
| --- | --- | --- |
| `git commit --amend` | 강서연 | 아직 push하지 않은 개인 커밋의 메시지 수정 |
| `git reset --soft HEAD~1` | 김수민 | 아직 push하지 않은 개인 커밋 취소와 변경 보존 |
| `git revert` | 윤정민 | push된 변경을 새 취소 커밋으로 되돌려 기존 기록 보존 |
| `git stash` / `git stash pop` | 임재홍 | 미커밋 작업 보관·전환·복원, 새 파일 포함 여부와 복원 충돌 확인 |

- 네 종류를 모두 수행하고, 모든 팀원이 최소 한 시나리오의 기록 작성에 참여합니다.
- `docs/troubleshooting-log.md`의 양식에 참여자·역할, 시작 상태·재현 절차, 명령, 결과, 주의점, 선택 이유와 증빙을 남깁니다. 다른 팀원이 읽고 따라 할 수 있게 적습니다.
- amend와 reset 실습은 개인 브랜치의 미공유 커밋을 대상으로 합니다. reset 실습은 이전 커밋이 있는 상태에서 진행합니다.
- 원격에 push된 변경을 취소할 때는 기존 기록을 보존하는 revert를 기본으로 하며, main 반영은 PR을 거칩니다.
- 보너스 rebase는 개인 feature 브랜치에서 진행하고 정리 전·후를 기록합니다. 커밋 식별자가 바뀌므로 이미 공유했다면 다른 팀원의 사용 여부와 영향을 확인하고 먼저 합의합니다.

## 개인 기여와 제출 증빙

팀장 포함 모든 팀원은 아래 기준을 충족합니다.

- 본인이 만든 PR 최소 2개가 main에 병합되어야 합니다.
- 본인 PR을 제외한 다른 사람 PR에 리뷰를 최소 2개 작성합니다. 기본 운영은 서로 다른 PR 2개 이상을 검토하는 방식입니다.
- 본인 PR에서 실제 리뷰 의견을 최소 1회 반영하고, 수정 커밋·답글로 증빙합니다.
- 담당 함수와 사용 예시를 완성하고 결과물 기여 커밋을 최소 1건 남깁니다.
- 트러블슈팅 시나리오 최소 1개의 기록 작성에 이름·역할이 드러나게 참여합니다.

각자 본인 Issue·PR·작성한 리뷰·리뷰 반영 커밋 또는 답글·실습 기록 링크를 제공합니다. 임재홍이 `SUBMISSION.md`에 팀원별로 정리하며, 링크는 다른 곳에서도 열 수 있도록 전체 URL로 적습니다.

필수 문서 3종과 README·SUBMISSION.md를 완성하고, `git log --oneline --graph --all` 결과 텍스트 또는 스크린샷을 히스토리 증빙으로 남깁니다. 실습을 실제로 수행한 뒤 상황·절차·결과·주의점을 기록합니다.

## 대면 진행 순서와 규칙 변경

- 대면 때 초기 구조 PR을 먼저 병합하고, 그 초안을 보완한 문서 PR과 각자 기능 PR을 진행합니다. 후속 PR은 초기 구조 반영 후 변경 파일이 본인 작업 범위에 맞는지 확인합니다.
- 문서·기능 등 모든 작업은 Issue와 PR로 추적하며, 대면 실습 후 남은 기여 횟수와 증빙을 함께 점검합니다.
- 긴급 수정도 최신 main에서 작업 브랜치를 만들고 Issue → 수정·검증 → PR → 리뷰·승인 → 병합 순서를 따릅니다. 배포 대상이 있으면 배포 후에도 확인합니다.
- 규칙 변경은 팀에 이유를 공유하고 합의 내용을 문서 수정 PR에 남깁니다.
